# 开发规范

记录踩过的坑，改插件和网页前先看一遍。带「测试」的条目有自动检查，`uv run pytest` 会拦下来。

## 注入页面的滚动性能

插件的浮窗和弹层挂在 gmgn 这类很忙的宿主页面上，主线程经常被宿主占满。滚动一旦需要主线程参与，宿主一忙就卡。

### 1. 滚动容器必须有不透明背景（测试）

凡是 `overflow:auto / scroll` 的元素，同一条 CSS 规则里必须写不透明背景，一般是 `background:var(--card)`。

- 原因：1 倍屏（大部分外接显示器）上，Chrome 不给透明背景的滚动容器做合成线程滚动，每一帧都回到主线程重绘。2 倍屏的 Mac 上看不出来，所以容易漏。
- 出过两次：0.9.30 的浮窗 `.list`，0.9.36 的最近 CA 面板 `.rc-list`。后者修复前滚动 160 次滚轮，主线程 Layerize 144ms，修复后 9ms。
- 父元素有背景不算数，必须写在滚动元素本身。
- 测试 `test_injected_scroll_containers_have_opaque_background` 会扫 `extension/content.js` 和 `extension/feed.js` 里的 CSS 规则。

### 2. 列表增量更新，不整段重建

- 列表用 `WechatFeed.syncList(container, items, keyOf, htmlOf)`：只替换 HTML 变了的节点，图片、hover、滚动位置都保留。不要对列表容器写 `innerHTML`。
- 卡片 HTML 里不能有随时间变化的文字（「刚刚」「3 分钟前」）。用 `freshHtml()` 输出固定标记，由 `tickFresh()` 定时填写，否则每次刷新都会判定变化、重建节点。
- 新建节点才需要 `hydrate()` 补图片，用 `syncList` 的返回值，不要对整个列表调用。

### 3. 长列表跳过屏幕外的布局

条数可能上百的列表，子元素加 `content-visibility:auto; contain-intrinsic-size:auto <估计高度>`，顶部插入新卡时不必重排整列。

### 4. 怎么验证

- 改完滚动相关的样式，跑测量脚本，参数传 `1` 模拟 1 倍屏（脚本会加载真实插件打开 gmgn，需要本地服务在跑）：
  - 浮窗：`uv run --with playwright python scripts/scroll_float.py 1`
  - 最近 CA 面板：`uv run --with playwright python scripts/scroll_recent.py 1`
  - 第二个参数可以注入一段 CSS，对比改前改后，例如 `".rc-list{background:var(--card)}"`。截图在 `.scratch/shots/`。
- 看两样：滚动瓶颈截图上不应该出现 `main thread scroll repaint`；滚动期间主线程的 Paint、Layerize 应该是个位数到十几毫秒。

## GMGN 额度

- 免费档每秒 5 权重，后台最多用约 2.5，实时解析新 CA 永远优先。新增任何会调 GMGN 的功能，先看「GMGN 用量」页的实测平均值和峰值，再算新增的权重/秒，写进代码注释。
- 页面展示优先读本地 `ca.db`，不直接打 GMGN；需要更新的走后台刷新队列（`CaStore.next_due`），不另开请求通道。
